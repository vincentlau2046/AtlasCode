## 1. 落码规格（Main 车道）

### 1.1 FX-27 — `PermissionRequest` hook `updatedInput` 未重查 `permissions.deny`（真实缺口，修前红）

- **缺口定位**：`src/tui/hooks/toolPermission/PermissionContext.ts:282-288` — `runHooks` 内 hook `permissionRequestResult.behavior==='allow'` → `finalInput = decision.updatedInput ?? updatedInput ?? input` → `handleHookAllow(finalInput, …)`；`PermissionContext.ts:370-381` `handleHookAllow` 直接 `buildAllow(finalInput, {decisionReason:{type:'hook',hookName:'PermissionRequest'}})`，**无 deny 规则重查** → hook 改写入参可绕 deny = 权限绕过。
- **对照（证明原语在场，engine 车道已做）**：`src/engine/pipeline/toolExecution.ts:323-333` PreToolUse hook `updatedInput` → `effectiveInput` → 门 `checkPermission(tool, effectiveInput)` 重判（L327 注「门在钩子改写后的 effective 入参上重判」）。
- **改法（1 处主改）**：`handleHookAllow` 在 `buildAllow` 前对 `finalInput` 重跑 deny 评估。原语齐（复用，不新造）：
  - `src/tui/utils/permissions/permissions.ts:927` `checkRuleBasedPermissions`
  - `permissions.ts:272` `getDenyRuleForTool`
  - `permissions.ts:153` `matchingRuleForInput`（pathValidation 支）
  - 命中 deny → 转 `buildDeny`（`PermissionContext.ts:352` 既有方法），decisionReason 指向命中的 deny 规则（非 hook）。
- **coordinator 车道**：`coordinatorHandler.ts:33` `ctx.runHooks` → 同 `handleHookAllow`，同缺口，**随主改一并覆盖**（共享同一 handler）。
- **零回归约束**：`updatedInput` 未命中任何 deny 规则 → `buildAllow` 行为与现完全恒等（不得改变 hook-allow 正常放行路径的 decisionReason/副作用）。

### 1.2 FX-37 — `permissions.deny` 不覆写 hook `permissionDecision:"ask"`（验证型，live 已绿）

- **不变量已双车道实现**（无缺口，本项 = 加回归断言锁定不变量，非修码）：
  - engine 车道：`src/engine/pipeline/toolExecution.ts:146-158` `mergeHookPermission` — L151 `if (!gate.allowed) return gate` **先于** L153-156 hook-ask 支（门 deny 不被 hook ask 降级）；头注 L140-143 明书「门已拒时门优先，ask 不覆盖 deny」。
  - TUI 车道：`src/tui/utils/permissions/permissions.ts:1014-1035` `hasPermissionsToUseToolInner` step 1a（L1026-1027 `getDenyRuleForTool` → 即拒）**先于** hook/classifier 步（L798 起）→ 规则序天然保 deny 优先。
- **Main 落码 = 0 行**（仅新增下方 §2 判别单测；若单测暴露 step 序残差则转小修，判据见 §2）。

### 1.3 AD-49 — `MCP_CONNECTION_NONBLOCKING` + `-p` 模式 5s 有界连接（落码，3-4 文件）

- **现状缺口**：`MCP_CONNECTION_NONBLOCKING` 全仓 0 命中（新 env）；headless 阻塞全连接 = `src/cli/print.ts:590-595` `await Promise.allSettled(… mcpManager.connect(name, config))`（慢服务器拖启动）；per-连接超时 = `MCP_TIMEOUT || 30000`（`src/tui/services/mcp/client.ts:406-409` + `src/mcp/mcpConnectionManager.ts:60-63` 双处同源 30s 常量）。
- **改法（3 件，原语均在场）**：
  1. **`MCP_CONNECTION_NONBLOCKING` env**：managedEnv 白名单 `src/tui/utils/managedEnvConstants.ts:122`（已含 `MCP_TIMEOUT`，可并列加）→ `-p` 模式下该 env=true 时**跳过 connect 等待**；慢服务器 → 走既有 pending 占位：`print.ts:297-300` `syncMcpClientRegistryLocal` 对 `getPendingServerNames()` 推 `{name, type:'pending'}` 占位（tool 池缺该服务器但进程不阻塞）。
  2. **`--mcp-config` 源 5s 连接预算**：`mcpConnectionManager.connect` 的 race 超时**参数化**（现 30s 常量 L60-63）→ `--mcp-config`（`src/cli/parse.ts:574`）源服务器走 5s 预算，其余源（settings/.mcp.json）维持 30s（零回归）。
  3. **源区分**：`buildMcpServerConfigs`（`print.ts` discoveryInput 面）按 `--mcp-config` vs settings/.mcp.json 分流超时预算；`--strict-mcp-config`（`parse.ts:729-730`）语义不变。
- **约束**：非 `--mcp-config` 源 30s 行为逐字恒等；`MCP_CONNECTION_NONBLOCKING` 缺省（未设）时行为与现完全一致（不得默认翻非阻塞）。
