## §3 残余 RED：G5d——surrender 保底形 = 全盲形态（设计级）

**现象**：G5 场景 turn-1（1200 行流式 + ask Write dialog）完成后，后续 SAY_HELLO 回合**请求链正常推进**（proxy call5/call6 wire 在案）、回合正常完成，但**响应零渲染**——`gate-check-ok` 全流 0 命中，屏面仅剩常驻提示行。

**代码直证链**：
1. 1200 行已完成消息 = 单条消息；收缩帽为**消息条数**语义（`computeSliceStart` cap=条数）→ 单条超视口消息不可被收缩 → 「流式压缩下限不可收敛」必然成立 → `resolveShrinkDecision` 2 次尝试耗尽 → surrender（正是 Main 修形说明预期的不可收敛场景）。
2. fallback 形 = `{ capRows: 0, streamingCapRows: 0, suppressStreaming: true }`（viewportBudget.ts:114）→ Messages `computeSliceStart(cap=0)` → `renderableMessages = []` → **消息区渲染零行**。
3. 复位面（resize / bottom 槽高度变化）后重测 → 2 次尝试内再次 surrender → **稳态全盲**；新回合触发不了复位（输入框高度恒等 + fallback 早退收缩环）。

**判据形冲突**：f4 冻结判据 2 之「surrender → 历史进滚动区（提示行在场）」在 inline 车道**不成立**——cap 0 + suppressStreaming = 内容不被渲染，不渲染 ≠ 进滚动区（inline TUI 不打印即不存在于字节流，wire 实证）。用户面 = 发消息、回合完成、**看不见任何回复**。

**定性**：非崩溃回归（钉底/不崩/可交互全保），为 fallback 保底形的可见性设计缺口。f4/Main 裁定选项（e2e 侧中立呈报）：
- A. fallback 重设计：保底形保留**最新回合**渲染（如 tail-cap 消息区或新回合重开 episode 并豁免当回合渲染）；
- B. 收缩帽改行数语义或对超视口单条消息加行级帽，使 compress 可收敛、surrender 概率归零；
- C. 判据再冻结：接受全盲形（e2e 侧认为不可接受——回复不可见 = 波目标「输入框钉底且交互可用」的自伤面）。
